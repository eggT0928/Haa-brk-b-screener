# 가족 초대·승인 및 공유 공간

작업 브랜치 `feat/family-access`. 한 가족(관리자 1명)의 개인용 앱이며 조직·다중 가족 서비스는 아닙니다. Firebase 프로젝트 IAM 권한을 부여하지 않고 **앱 사용 권한만** 관리합니다.

## 사용법

1. 현근 관리자 계정으로 로그인하고 **가족 초대·권한 관리**를 엽니다.
2. 초대할 Google 이메일을 입력하고 두 포트폴리오의 조회·편집 허용에 동의한 뒤 초대를 등록합니다.
3. 표시된 앱 링크를 전달합니다. 이메일 자동 발송은 하지 않습니다. 초대는 14일간 유효하며 해당 이메일로 Google 로그인하면 구성원으로 승인됩니다.
4. 초대되지 않은 로그인 계정은 데이터를 볼 수 없습니다. 본인이 **관리자에게 승인 요청**을 누르면 관리자 화면에 표시됩니다. 관리자가 승인하거나 거절합니다.
5. 관리자는 초대 취소와 구성원 접근 해제를 할 수 있습니다. 해제된 계정은 관리자 재초대가 필요합니다. 관리자 본인의 해제나 다른 관리자로의 승격은 앱에서 제공하지 않습니다.

등록 시점에 Firebase Auth 사용자가 없어도 이메일 초대는 가능합니다. 실제 Google 로그인 이전에는 `로그인 대기`이며, 이를 가입 완료로 표시하지 않습니다. 공유 링크 자체는 비밀 승인 토큰이 아니므로 링크를 알아도 승인된 계정이 아니면 데이터에 접근할 수 없습니다.

## 기존 데이터 보존과 역할

- 현근·수진 보유수량과 계산안 이력은 기존 현근 UID 아래 그대로 유지합니다. 이관·복사·임의 초기화하지 않습니다.
- 구성원의 `access/{uid}.ownerUid`를 기존 현근 UID로 서버에서 발급합니다. 두 계정의 화면이 같은 경로를 구독하고 저장합니다.
- 현근 보유수량: `users/{ownerUid}`. 수진 보유수량: `users/{ownerUid}/portfolios/sujin`.
- 각 포트폴리오의 `rebalances` 하위 컬렉션에 계산안을 추가합니다. 기존처럼 이력 수정·삭제는 금지합니다.
- 관리자와 구성원 모두 두 포트폴리오를 편집합니다. 사람별 읽기 전용·일부 포트폴리오 전용 권한은 없습니다.
- 동시 편집은 자동 병합하지 않습니다. 먼저 저장한 내용을 다른 기기에서 확인하고 편집하세요. 같은 문서의 나중 저장이 최종값입니다.
- 접근 해제는 서버 읽기·쓰기를 거부하고 앱의 실시간 승인 구독에도 반영합니다. 이미 화면에 표시되거나 사용자가 복사한 정보를 원격으로 회수하는 기능은 아닙니다.

## 권한 저장과 서버 검증

| 경로 | 내용 | 접근 |
|---|---|---|
| `internal/family` | 고정 관리자 UID·이메일 | 서버만 |
| `access/{uid}` | enabled, role, ownerUid, email | 본인 읽기, 서버 쓰기 |
| `familyInvites/{sha256(email)}` | 정규화 이메일·14일 만료·초대 상태·수락 UID | 서버만 |
| `familyRequests/{uid}` | 명시적 승인 요청·상태 | 서버만 |
| `familyAudit/{id}` | 관리자 작업·대상·시각 | 서버만 |

API는 Firebase ID 토큰의 서명·만료·폐기를 검증하며, 권한 등록에는 이메일 인증된 Google 로그인을 요구합니다. 관리 API는 서버 설정의 소유자 UID와 `admin` 승인 문서를 모두 확인합니다. `ownerUid`나 `role`을 요청 본문으로 지정할 수 없습니다. 첫 방문자를 자동 관리자로 지정하지 않습니다.

- `POST /api/access/session`: 본인 초대 수락과 상태 확인. 이메일·UID는 요청 본문이 아닌 검증한 토큰에서 읽습니다.
- `POST /api/access/request`: 본인 승인 요청. 동일 UID 대기 요청은 중복 저장하지 않으며 거절 후 하루 동안 재요청을 제한합니다.
- `GET /api/access/manage`: 관리자만 구성원·초대·요청 목록 조회(컬렉션별 최대 100건).
- `POST /api/access/manage`: 관리자만 invite/cancel/approve/reject/revoke. 변경과 기록은 트랜잭션으로 적용합니다.

동시에 같은 이메일 초대를 수락해도 하나의 UID만 성공합니다. 초대 취소 후 수락은 실패하며, 수락 후 초대 취소는 오류로 알려 구성원 접근 해제를 사용하게 합니다. 거절 시 남아 있는 대기 초대도 취소합니다. 승인 요청을 처리할 때는 현재 Firebase Auth 계정의 이메일·Google 제공자·비활성 상태도 확인합니다.

별도 함수·Scheduler·메일 발송 서비스는 추가하지 않습니다. 기존 API 함수와 Firestore 읽기·쓰기만 사용합니다. 비용 0원이나 지출 상한을 보장하지는 않습니다.

## 최초 관리자 초기화 (신뢰된 운영자만)

새 환경에서는 먼저 관리자 본인이 Google 로그인하고, Firebase 콘솔에서 정확한 UID의 `access/{UID}.enabled`를 boolean true로 승인합니다. 기존 환경은 이미 승인된 소유자를 사용합니다. **IAM 소유자 초대와 이 앱 승인은 별개입니다.**

Firebase CLI 로그인 후 저장소 루트에서 정확한 프로젝트와 이메일을 명시합니다. 아래 이메일·프로젝트는 예시이며 실제 운영 값으로 바꿉니다.

```bash
# 읽기 점검만. 현재 Google 계정과 기존 승인 여부 확인
node scripts/bootstrap_family.cjs --project YOUR_PROJECT_ID --owner-email OWNER@gmail.com
# 동일 확인 후 승인된 기존 소유자를 앱 관리자로 연결
node scripts/bootstrap_family.cjs --project YOUR_PROJECT_ID --owner-email OWNER@gmail.com --apply
```

초기화는 `internal/family`와 기존 `access/{UID}`의 관리자 관련 필드만 원자적으로 설정합니다. 읽은 문서의 갱신 시각을 선행 조건으로 사용하며, 다른 공유 공간이 이미 설정된 경우 중단합니다. 사용자 보유수량·이력·신호·IAM·결제는 변경하지 않습니다. 토큰이나 서비스 계정 키를 저장소·프런트엔드에 넣지 마세요.

## 배포 및 검증

사용자 승인 후 기존 전용 프로젝트에 규칙·API·Hosting을 함께 배포합니다. 운영과 에뮬레이터를 혼용하지 않습니다. 아래 배포 명령은 실제 운영 변경입니다.

```bash
npm test
pytest -q
npm run test:rules
npx firebase emulators:exec --project demo-haa --only firestore "python scripts/check_emulators.py"
npm run build
npx firebase deploy --only firestore:rules,functions:haa:api,hosting --project haa-portfolio-260830
```

공유 예약 함수 자체는 바뀌지 않으므로 이번 기능은 API만 갱신합니다. GitHub Actions는 코드·규칙·실제 Firestore 트랜잭션 검증만 하며 배포나 main 머지를 수행하지 않습니다.

초대 수락·미승인 차단·해제·재초대·동시 수락·자기 관리자 보호·공유 경로 저장·늦은 HTTP 응답의 권한 복원 방지 등을 자동 검증합니다. 운영에서는 실제 수량을 테스트 값으로 변경하지 않고 기존 문서 갱신 시각과 지문으로 보존을 확인합니다.

롤백은 Hosting과 API, 규칙을 맞는 이전 버전으로 재배포합니다. 이전 버전은 가족 공유가 없으므로 구성원은 일시적으로 이용하지 못할 수 있습니다. 권한 문서나 포트폴리오 데이터를 삭제하는 방식으로 롤백하지 마세요.
